# Built-in plugins

The first-party plugins shipped with Botling (plugin-platform.md §3.4, step M11). Each folder is a plugin
as the plugin library holds one (`package.json` with a `ccb` field), and the registry loads it by the same
path: `build-builtin-plugins.mjs` builds them into `out/builtin-plugins/`, and electron-builder copies that
beside app.asar (`Botling 2.app/Contents/Resources/builtin-plugins`). They are read-only, on until you turn
one off in the Plugins page, and never wait for approval. A plugin of the same name in the library replaces
one, which is how Maintainer changes a built-in plugin: it copies the folder into the library.

| Plugin | What it brings |
|---|---|
| `ccb-latex` | KaTeX in messages and the input box (`$…$`, `$$…$$`, `\(…\)`, `\[…\]`), Mod+Shift+M. Botling Web (the phone, which runs no plugins) bundles its web part into the chat page instead. |
| `botling.board` | Pins (the Board it once drew was removed 2026-11-11; the name stays, its data is keyed by it): the chips of pinned components above the input box (and the sheet a chip raises), pins floating in a corner of the window, and the pin / ↻ / ⋯ bar over a component in a reply. All of it is drawn in the chat page by its web part, from the page's own parts (`ccb.page`, Web/src/plugins.ts `PageKit`: the state, the slots `pinArea` / `overlay`, the words, the clocks and the component frames, so a pin's card is the page's own card) the page's `ccb.messages.cardBar`, and the component studio's `ccb.studio.specButton` (the pin in the head of a component made from a reply). What a pin is, where it sits and when its command runs is the plugin's program part (its storage; the core's `pins.json` is imported once). Botling Web bundles its web part, as ccb-latex's. |
| `botling.cards` | The web preview card (`網頁預覽卡片`). A component of the same name in the library (`ccb-components`) still wins. |
| `botling.chat-extras` | Pictures in a row of a reply become one gallery, a long message of yours folds to its first lines (Show more), and a long paste waits as a chip above the input box (its limits are this plugin's settings; the ones Botling's own settings had move here once). Botling Web bundles its web part, as ccb-latex's. |
| `botling.design` | `/design` in the / menu, put into the message as words; the bots' rules say what it means. |
| `botling.catchup` | Chat summaries: unread replies folded into a summary card when you read a chat (`chatRead`), intervals between your messages, sources in a dialog. Its program part reads the chat (`chat.messages`), runs the isolated claude/codex one-shot call (`engines.cli`) and puts each summary in the chat as a message decoration (`chat.decorate`), which its web part draws (`ccb.decorations`, Web/src/decorations.ts). Its settings show under Settings → General → Chat summaries (`hidden` on the Plugins page). The first run takes over the core's old `catchup-summaries.json` and settings.json keys without changing them. Botling Web bundles its web part, as it does ccb-latex's. |
| `botling.git` | App-managed git worktrees (Worktrees block under a bot's tasks: `rightPanel.section` view), the program part and ReviewView for reviewing their changes (diffs, comments sent to the agent, per-turn changes; no view shows it since 2.6.0: the header's Review tab is gone), commit and pull request, and a Worktrees page in Settings (`settings.section`; the toggle and folder the Developer page had, moved once from settings.json). It decides which folder each bot's session starts in (`api.sessions.setFolder`, permission `sessions`, built-in plugins only): Botling keeps the answer in memory and on disk, so a turn never waits for the plugin host and the first turn after a restart is already in the worktree. The agent's wake note about its worktree comes with that folder. Runs git and `gh` itself (`exec`). Its program part keeps the worktree lists and recorded turns where the core kept them (`worktrees.json`, `review-turns.json` beside each bot's chat files). |
| `botling.dev` | The developer tools for the project that is Botling's own source (Settings → Developer): `<install-build path="…">` (a card in the main bot's chat; on Install the plugin writes the install script and its state, then asks the app to restart: `api.app.installAndRestart`, permission `app`, built-in plugins only; a build that does not come up is rolled back by the script and told to the bot that asked), `<app-screenshot/>` (`api.app.captureWindow`) and the briefing the developer project's manager hears at each wake (pushed with `api.app.briefing`; Botling keeps it, so a wake never waits for the plugin). What stays in the core: the `healthy` handshake the script waits for (`core/self-update.ts`: it must not depend on this plugin being on), the checkpoint of running work and quitting (`app.installAndRestart`'s core side), newer-release notices, and the "Not right" flag on a reply (its popover, the window picture of the chat as you saw it and the report, `Core.reportFeedback`). |
| `botling.usage` | The quota rings in the sidebar gear's popover (Claude, Codex, Antigravity; `quickSettings` view) and Settings → Usage (`settings.section` view, with the "Usage by bot" link in the popover). Botling still collects the numbers (`core/usage.ts`, `quota.ts`); the plugin reads them with `api.usage.view()` through its program part and draws them in two sandboxed frames, refreshing on open, after a bot's turn (its program part counts `turnFinished`), and each minute. |
| `botling.report` | Report pages for the bots: the report skill (`skills/report/`: its `SKILL.md` and the ReportSpec v2 guide `report-blocks.md`, listed in `agentContributions()` for every engine), the command (`agentCommands`: the app's `--render-report spec.json page.html`, bundled as `report.cjs` with its licence notices; the renderer code stays in `desktop/reports/`) and the rule that tells every bot to use them (`promptSections`, after the results rule; the text carries `{{command}}`, `{{docs}}` and `{{artifacts:…}}`, filled in per bot). Claude does not load the skill natively: bots read the guide by the path the rule names, before every spec. The rule is the short contract only; every writing, template and chart rule lives in the guide, and `{{docs}}` names a stable link (`<data>/core/plugin-guides/botling.report/…`) to the plugin folder whose renderer runs (a rebuilt one in `<data dir>/plugin-overrides`, else the shipped one), so a guide rebuilt there reaches the next report with no restart and no prompt change. |
| `botling.routines` | The Routines button in the chat header (a `chatHeader` view: a button with the view's title that opens a popover under it holding the plugin's frame for the bot on screen): a bot's routines.cron lines and the app's own schedules, with Pause, Resume and Cancel. Botling still keeps, runs and schedules them (`core/routines.ts`, `session-schedules.ts`, the routines protocol in `spec/`); the plugin's program part lists and changes them through `api.routines.list` / `api.routines.change` (permission `routines`, built-in plugins only; pause, resume and cancel, never create). |
| `botling.terminal` | The Terminal under the chat: the Terminal button in the chat header (Mod+J, `bottomPanel` view with its `toggle` command) shows tabs of real shells in the bot's project folder, one list per bot, kept running while the panel is hidden. The program part owns the pseudo-terminals (`node-pty`, staged beside it in the plugin's own `node_modules` by the build: `nativeModules` in build.json) and answers its frame through one exposed method, `terminal`; what a shell prints reaches that bot's frames as a push (`api.ui.emit`, `ccb.on("terminal", …)`). The frame draws the tabs with xterm.js and the Meslo font (inlined), sends keys and acknowledgements one request at a time (merged while one is on its way), and hands a key with ⌘ held to the page's shortcuts (`ccb.forwardKey`). The page lays the panel out (divider, height, the header button, focus); the key is the page's own to run (it asks the frame, which knows whether it has a shell to show). Needs `exec` (`api.bots.folder`: the folder is the bot's own, a frame cannot choose one). A key chosen for the old `toggleTerminal` shortcut moves to `botling.terminal.toggle` once. |

The `choices` card is not here: the chat draws a reply's `<choices>` as buttons by itself, and a `choices`
component in the library replaces them, as before. Shipping a template here would change how questions look
for everyone without one.
